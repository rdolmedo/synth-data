# GLM-5.3-Flash agentic-generation throughput on one 8xB200 node (vLLM 0.31)

Goal: the most generated tokens/s for terminus-2 rollouts (billion-token runs) on one 8xB200 node
(cpu404), with rollouts capped at a 132k-token context. Measured on 2026-10-15 with the replay
benchmark described below. Raw results, time series and every config's vLLM log are in
`/data/aai/tbench/throughput/<config>/`.

## TL;DR

| node config (8xB200) | gen tok/s (node) | x prod (measured A0 peak, 4.6k) | B tok/day | rollouts/day* |
|---|---|---|---|---|
| production 2026-10-14 (FP8, 2x DP4+EP4, MTP3, 8832-token prefix granularity) | 4,000-4,600 | 1.0 | 0.35-0.40 | ~9k |
| FP8 + `--prefix-match-unit 128` + MTP1 (same weights) | ~8,200 | ~1.8 | 0.71 | ~17k |
| **NVFP4 + `--prefix-match-unit 128` + MTP1 + FlashInfer MoE, 2x DP4+EP4 (recommended)** | **~10,900** | **~2.4** | **0.94** | **~22k** |
| same, one DP8+EP8 group | ~8,400-8,700 | ~1.85 | 0.72-0.75 | ~17k |

\* At the measured 42k generated tokens per rollout (glm-v* trajectories cut at 132k context).

Launch with `inference/serve_node.sh` (defaults are the recommended config; the proxy port is the
only endpoint the dispatch workers need). Run it at about **400-500 concurrent rollouts per node**:
the NVFP4 plateau is flat from 192 to 384 agents per 4-GPU group. FP8 configs fall off a cliff
when over-admitted (see below).

Three changes carry the gain:

1. **`--prefix-match-unit 128` (1.7x at equal load).** By default vLLM 0.31 matches prefixes in 8832-token blocks
   for this hybrid model, and MTP drops another whole block on every hit. Each agent turn therefore
   re-prefilled about 13k tokens; with this flag it is about 3k (only the new tokens). See
   "Why re-prefill dominated".
2. **MTP1 instead of MTP3.** Throughput at equal load is the same (3,538 vs 3,501 tok/s per group),
   but MTP3's speculative KDA state holds about 1.5x the KV per running request. MTP1 therefore keeps
   prefix hits on the GPU and peaks higher (4,108 vs 3,501 tok/s per group).
3. **The NVFP4 checkpoint (`nvidia/GLM-5.3-Flash-NVFP4`) with FlashInfer TRT-LLM FP4 MoE kernels
   (+33%).** It frees 29 GiB per GPU for KV (11.7M vs 7.6M tokens per rank) and runs FP4 tensor-core
   MoE. Its outputs come from a quantized model; see Caveats.

Also fixed: the launchers never put the venv's `nvcc` on PATH. vLLM's `has_flashinfer()` requires it,
so every FlashInfer MoE kernel was silently disabled: NVFP4 fell back to weight-only Marlin, and
FP8 used DeepGEMM. For FP8 this made no measurable difference (FlashInfer 4,143 vs DeepGEMM 4,108
tok/s), but NVFP4 needs it. The option is `FLASHINFER_MOE=1` in `serve_glm_dpep.sh`, on by default
in `serve_node.sh`.

## Workload model and method

* **Replay benchmark** (`inference/replay_bench.py`, driver `inference/bench_config.sh`): N concurrent
  agents replay recorded GLM terminus-2 trajectories (glm-v1/v2/v3/v5, 1593 rollouts; result files
  sorted, per-agent RNG seeded by (seed, agent), so every config replays the same work in the same
  order). User turns (task prompt and terminal observations) are recorded. Assistant turns are
  generated by the server at temperature 1.0, with `max_tokens` set to about 1.5x the recorded turn
  length. They are fed back with `reasoning_content`, and the chat template keeps past thinking, so
  prompts only grow by appending. Measured: about 1.1-1.2k generated tokens per turn and 31-40k
  prompt tokens per turn on average.
* **Tool think-time** between turns: lognormal with median 3.6 s and sigma 1.48 (mean about 10.7 s),
  capped at 120 s. This is fitted to the glm-v* rollouts (agent wall time minus API time per turn:
  p25 1.3 s, median 3.6 s, p90 22.7 s).
* **132k cap.** A rollout ends when the next prompt would reach 132,000 tokens (client estimate:
  previous prompt + completion from `usage`, plus the new observation at 3.0 chars/token). The bench
  also goes through `sticky_proxy.py --cap-tokens 132000`, the production capping proxy with
  least-loaded conversation pinning. When a rollout ends, that agent starts the next trajectory
  from turn 1.
* **Steady state.** `--random-start` starts each agent's first rollout at a random recorded turn below
  the cap, with the recorded history as context, so the mix of short and long contexts is there from
  the start. The cold-prefill burst this causes is absorbed by the warmup: 9-10 min for the first
  concurrency level, 6-7 min each time agents are added. Levels were run back to back on one server,
  increasing concurrency.
* **Measurement windows** of 8-10 min per level. Server-side Prometheus counters are differenced over
  each window and summed over ranks:
  * generated tokens (the primary metric);
  * prompt tokens by source (computed, GPU prefix hit, CPU-offload hit);
  * preemptions and spec-decode acceptance;
  * TTFT and inter-token latency means.
  
  KV usage, running and waiting are sampled every 30 s. Client side: turns/s and per-turn latency
  p50/p90. Tables: `inference/tput_table.py /data/aai/tbench/throughput/*/results.jsonl`.
* **Running two configs at once.** 4-GPU (DP4+EP4) configs ran two at a time on GPUs 0-3 and 4-7, each
  with its own proxy and bench. Node-level numbers for the 2x DP4 layout are twice the per-group
  numbers.
* **Noise.** The two halves of each window agree to within 1-8% (2-min chunk CV 0.01-0.08 below the
  knee, about 0.13 past it). Each config ran once, so treat differences under about 10% as ties.

DP8 gives each GPU 18% more KV (13.9M vs 11.75M tokens per rank). But it runs 20-23% slower at the
same per-GPU load: inter-token latency is 61 vs 44 ms. Two causes:
* all 8 ranks step in lockstep, so any rank's prefill chunk stalls all eight;
* the MoE allgather/reduce-scatter spans 8 GPUs.

KV is not binding for NVFP4 at these loads, so the extra KV buys nothing. The 640-agent DP8 level
was not run (GPU time ended). With FP8 weights DP8 would add 75% KV per GPU (experts are 2x larger),
which could pay off near the FP8 cliff. Not measured.

Not shown: the first NVFP4 attempt (`old_partial/N1_nvfp4marlin`) ran on the Marlin fallback
(`FLASHINFER_MOE=0`) and was stopped after warmup.

## Why re-prefill dominated (and what `--prefix-match-unit` changes)

GLM-5.3-Flash has 34 KDA (linear-attention) layers and 11 sparse-MLA layers. vLLM sizes a block so
that one attention page is at least as large as one KDA state:
* KDA state: 64 heads x 128 x 128 fp32 = 4 MiB, plus the conv state, about 4.5 MB per layer;
* fp8 MLA: 512 B/token;
* result: an 8832-token block at TP1 (`Platform._align_hybrid_block_size`).

With prefix caching the mamba cache mode is `align` (`all` is not supported for this model). In
that mode, before this change:

* **Coarse match points.** A KDA state is only checkpointed at block boundaries, so a new turn could
  reuse at most `floor(prev/8832)*8832` tokens of the previous prompt.
* **Eagle block drop.** With MTP, every prefix hit additionally drops its last matched block
  (another 8832 tokens).

Each turn thus re-prefilled about 13k tokens when it adds only about 1k observation tokens plus the
previous answer. Prefill ran at 11x the generated tokens/s (23-25k vs 2.0-2.3k tok/s per group).

`--prefix-match-unit 128` hashes prompts every 128 tokens. The scheduler then ends a prefill chunk at
the prompt's last 128-token boundary (one unit lower with MTP), so the KDA state is stored there, and
the eagle drop shrinks to one 128-token unit. Measured: computed tokens per turn fall from 13k to
2.4-4k, and the generated share of GPU time rises accordingly.

Correctness (`inference/prefix_check.py`, needs `VLLM_SERVER_DEV_MODE=1`): for 7 recorded turn pairs,
a warm request restored from the previous turn's sub-block state had the same greedy agreement and
logprob gap as a second cold run of the same prompt:
* cold vs warm: 4-29 of 48 tokens identical, max |dlogprob| 0.18-0.27 before divergence;
* cold vs cold: 4-26 of 48 tokens identical, max |dlogprob| 0.07-0.27;
* fine-grained GPU hits combine correctly with 8832-granular CPU-offload hits.

Run-to-run nondeterminism (DP/EP batching) is the floor; no extra error is visible.

## MTP: 1 beats 3 for this workload

Acceptance is 40% for MTP3 (2.19 tokens per step) vs 63% for MTP1 (1.63). At equal load the
throughput is the same (P3 vs P1 at 128 agents: 3,501 vs 3,538). The difference is KV: MTP3's
speculative KDA state blocks make each running request hold about 1.5x as many KV blocks (3.5M vs 2.4M tokens, KV 50% vs
32% at the same 100 running requests). P3 therefore loses its GPU prefix hits at 192 agents and
collapses at 256, while P1 peaks at 192-256. MTP0 and MTP2 were not measured.

## The over-admission cliff

FP8 configs collapse once KV saturates. GPU prefix hits go to 0, everything is reloaded from the CPU
tier or recomputed, requests are preempted, and gen tok/s roughly halves:
* P3: 3,425 tok/s at 192 agents → 1,973 at 256;
* P1: 3,907 at 256 → 2,098 at 320.

The 2026-10-14 production run sat at this cliff (KV 70-95%). NVFP4 has 54% more KV per rank and
degrades gracefully instead: 5.4k → 5.3k → 5.1k → 5.5k tok/s from 192 to 384 agents per group, with
KV 30-66% and no preemptions.

## Recommended configuration

`inference/serve_node.sh` (defaults: `QUANT=nvfp4 LAYOUT=dp4x2`):

```
inference/serve_node.sh 8001     # proxy on :8001 -> ranks 8101-8104 (GPUs 0-3), 8111-8114 (GPUs 4-7)
```

* Weights: `nvidia/GLM-5.3-Flash-NVFP4`, at `/data/aai/models/GLM-5.3-Flash-NVFP4`; copied to
  `/tmp/$USER/models` on first start.
* Layout: two DP4+EP4 groups (GPUs 0-3 and 4-7), one API server per rank.
  `--enable-ep-weight-filter`.
* Speculative decoding: MTP with 1 speculative token.
* `--prefix-match-unit 128`; nvcc on PATH (FlashInfer TRT-LLM NVFP4 MoE).
* Unchanged from production: fp8 KV, mem util 0.92, 16k batched tokens, 256 seqs per rank,
  `--kv-offloading-size 120` (8 x 120 GiB = 960 GiB pinned host RAM).
* Front end: `sticky_proxy.py` with least-loaded conversation pinning, `--cap-tokens 132000`, and a
  pins file.
* **Admission:** 400-500 concurrent rollouts per node (200-250 per group). As a safety net run
  `gen/kv_throttle.py` with a band around `--low 0.65 --high 0.75`, using `--max-burst` and
  `--cooldown`.
* Same weights as production (official FP8): `QUANT=fp8 serve_node.sh`, at about 350-400 rollouts per
  node. FP8 falls off the cliff above about 250 per group, so keep the throttle band lower
  (`--low 0.55 --high 0.65`).
* First NVFP4 start on a node takes about 20 min, mostly FlashInfer autotuning, which is cached under
  `/tmp/$USER/vllm-cache`. Later starts take about 5 min. The cache tar on /data was refreshed with
  these kernels.

## Tokens/day projection (one 8xB200 node, steady state)

| config | gen tok/s | tokens/day | days per 1B tokens | rollouts/day (42k gen tok each) |
|---|---|---|---|---|
| production (A0) | 4.0-4.6k | 0.35-0.40B | 2.5-2.9 | 8-9.5k |
| FP8 P1 | 8.2k | 0.71B | 1.4 | 17k |
| NVFP4 N1 (recommended) | 10.9k | 0.94B | 1.06 | 22k |

Several billion tokens therefore take about one node-week per 6-7B tokens with the recommended
config. Several nodes scale linearly, since each node is independent behind its own proxy. Discount
by availability: restarts, rollouts lost to sandbox errors, and the dispatch pipeline keeping
400-500 rollouts in flight.

## Knobs considered and not measured

* **gpu-memory-utilization 0.95:** about +11% KV on FP8 (6 GiB per GPU). Under NVFP4 the throughput
  peak sits at 30-45% KV, so KV is no longer binding; skipped (OOM risk for little gain).
* **max-num-batched-tokens 32k/64k:** with `--prefix-match-unit` a turn computes about 3-6k tokens, so
  chunks rarely exceed 16k. Larger chunks would mainly lengthen DP lockstep stalls. Skipped.
* **Offload size:** CPU-tier hits are 0-17% at the NVFP4 operating point (40-60% only in overloaded
  FP8). 120 GiB per rank keeps 8 ranks at 960 GiB, under the 1 TiB budget. Not swept.
* **TP2 inside DP:** its point was a smaller block (about 4.4k tokens) to cut re-prefill waste, which
  `--prefix-match-unit` removes without halving KV. Skipped.
* **all2all / DBO / EPLB:**
  * DeepEP, pplx and nixl-ep are not installed in the venv; DBO requires one of them.
  * `flashinfer_nvlink_{one,two}_sided` exist but are untested here; the default is
    allgather_reducescatter.
  * EPLB on FP8 B200 forces the DeepGEMM path and needs redundant-expert memory.
  * Not pursued.
* **Async scheduling:** already on by default (spec decode + DP).
* **CUDA graph sizes:** the default captures up to 1024 tokens, which covers 256 seqs x (1+MTP).
* **mamba ssm cache dtype bf16:** would halve the block, but Glm5Next ignores the flag, and it changes
  numerics.
* **Context cap:** kept at 132k (user decision). Per-turn cost grows with context; a lower cap would
  raise rollouts/day more than tok/s.

## Caveats

* **The benchmark is a replay.** Observations are recorded, not produced by the generated commands.
  The model's answers diverge from the recording, so contexts grow like the recording, not like a
  live rollout. Tool time is a fitted distribution, with no real sandbox latency or failures. The
  132k cap is the client estimate plus the capping proxy. Relative results should transfer; absolute
  tok/s in production will be somewhat lower (idle gaps when workers start or finish rollouts, uneven
  load).
* **Single runs.** Each config ran once with 8-10 min windows (about ±5% noise). The two DP4 halves
  are different GPUs; N1 (GPUs 0-3) and N1b (GPUs 4-7) agree (5.4-5.5k).
* **Client vs server counts.** Client-side gen tok/s counts only completed requests and lags the
  server counter by up to 8% at high concurrency. The tables use server counters.
* **Rollouts/h from the bench** is inflated in the first level (first rollouts start mid-trajectory).
  Use tok/s ÷ 42k generated tokens per rollout instead.
* **NVFP4 is a different set of weights.** ModelOpt PTQ by NVIDIA: routed and dense MLP in NVFP4;
  attention, shared experts, router and the MTP layer kept in bf16. NVIDIA reports parity with BF16
  (TB 2.1 0.832 vs 0.826, GPQA 0.921 vs 0.922). MTP acceptance is identical to FP8 (63%), so token
  distributions are close. Still, SFT data generated with it comes from a quantized teacher. Spot-check
  before switching a billion-token run, e.g. about 100 rollouts on known tasks: pass rate and
  turn/length stats vs glm-v*. The FP8 path (P1) keeps the official weights at about 75% of the
  throughput.
* **Launcher coverage.** `serve_node.sh` was exercised end to end in `LAYOUT=dp8` mode: copy check,
  8 ranks, the capping proxy with a pins file, and the DP8 bench through its proxy with 0 errors. The
  default `dp4x2` mode starts two `serve_glm_dpep.sh` groups with exactly the measured N1 settings.
  Two such groups ran side by side all day, but not via `serve_node.sh`. Watch the first start.
* **`--prefix-match-unit` is a recent vLLM 0.31 feature.**
  * Verified for greedy agreement within nondeterminism (above) and over 10k+ turns without errors.
  * It adds about 1000 sha256 block hashes per 132k-token request, which is not a bottleneck here.
  * The CPU-offload tier still matches at 8832-token granularity.
