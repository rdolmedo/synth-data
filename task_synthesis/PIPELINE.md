- **plan** draws the specs in one seeded order and marks the ones that go to binding (`bind: pending`): a seeded
  `asset_share` of the eligible specs (bucket best-generated, anchor class not `crypto-material`, whose keys
  `scrub.py` redacts). It sizes the spec count from the budget (1.4x oversupply) and writes
  `<ROOT>/production/<name>/run.json` and `<ROOT>/rounds/<name>/specs.jsonl`.
- **The driver** submits the generator servers, the bind job, the round, the stream producer and, once the stream's
  first chunk exists, the Super campaign (`synth/campaigns/nemotron35-super-tasksynth-m1.toml` filled in). It restarts
  a dead server, bind job or producer, and logs `ALERT` lines in `driver.log`.
- **Binding streams.** `assets.bind run --round <name>` binds the pending specs in queue order and publishes each
  result as `<round>/bind/<spec>.json`, with the asset exported to `<round>/assets/<spec>/`. The round authors a
  pending spec only once its result is in: bound specs get the preset's author, the rest become ordinary generated
  tasks. A spec starts only while at most `--bind-window` (300) pending specs before it in the queue still wait for
  their result, so every time prefix of the generation (the pilot's 330M point, the ladder's fit data) keeps the
  planned real-asset share up to that many specs.
- **Binding throughput** (`m1.toml [bind]`, #133). Binding is limited by GitHub repository search (25 queries/min on
  one token) whenever specs land in cells the bind has not searched yet, and otherwise by slots x DeepSeek latency
  (a spec in a known cell holds its slot ~4 min). So: 600 slots (or `concurrency_per_server` x servers), cells
  start from earlier binds' candidates (`warm_from = "auto"`; their bound specs count toward MAX_USES 2), and a
  new cell runs its first `grow_now` (3) queries per catalog for the waiting spec, then the rest of its k in the
  background at low gate priority.
- **One round, two kinds of task.** `round --real-assets <preset>` sets the bound specs' author recipe. Its efforts
  reach bound specs only (`--effort-scope asset`, default): unbound specs keep student 1's one-shot recipe, with the
  author and judge at the server's effort. Records carry `spec.bind` and `effort`.
- **Stop.** The driver writes `<round>/STOP` once the campaign's projected tokens, plus the streamed-unopened and
  accepted-unpublished tasks at the running tokens per trace, reach the budget x 1.10. The round then cuts its open
  sessions and the driver releases the generator servers. The campaign runs at max concurrency until the budget
  ("saved"), then cuts its live attempts and keeps them as truncated data. `driver.log` records the time each
  `--milestones` mark of saved tokens is passed.
- **Super follows supply (#234 R1).** The campaign starts with `[campaign.autoscale] start` engines (2) and the
  controller adds one when demand (active + dispatchable attempts) exceeds the engines' kv_fit limit by one engine for
  `up_seconds` (5 min), and drains one below `down_util` (50%) for `down_seconds` (15 min), up to `[campaign] engines`
  and the live cap `ops/admission-policy.json serving_jobs` (never submitted above it). State and decisions:
  `ops/progress.json` `autoscale`, `status.log` "Serving autoscale". Replay a finished campaign's supply under other
  thresholds on CPU: `python -m synth.analysis.autoscale_replay --campaign <dir> [--grid]`.
- **Decontam hold (#127, #234 R2).** While `<run>/decontam.HOLD` exists, the driver keeps one server from the round's
  STOP (the HOLD's `keep`, else the one with the most judge load in `<work>/judge-load/`, else the first healthy) and
  releases the others; it releases the last one within ~30 s of the HOLD's removal. No HOLD: servers go at round
  finish, as before.
- **/data file quota.** `plan` estimates the run's files (`[quota] files_per_task` x tasks + the campaign's loose
  attempts) and warns if the run would leave fewer than `alert_free_files` free. The driver checks `lfs quota` every
  pass and logs an ALERT below `alert_free_files`, at most hourly; it never stops a run (user, 2026-11-04).
  `launch` warns too (no refusal; user, 2026-11-05) when the run's remaining expected files (tasks not started x
  `files_per_task`, plus the campaign's loose files unless it is complete) exceed the free files (#245).
- **Pack finished rounds (#245).** A round writes ~38 loose files per accepted task (m1-hero: ~2.45M).
  `python -m task_synthesis.pipeline.roundpack plan --round <r>` is a dry run; `submit --round <r> --delete` packs
  `work/` and `tasks/` into `packed/round-NNNNN.zip` + `records-NNNNN.jsonl.gz` (5,000 specs each) + `index.json`
  in a CPU job. It refuses while a round job is queued, before the round is finished, and (production) before the
  stream ENDed and the decontamination list is published; `--force` packs on demand. A loose file is deleted only
  when its zip member has the same size and CRC32. Every round reader goes through `roundpack.RoundFiles` (packed,
  partly packed or loose; consistent while a pack runs); tools that write into a round refuse a packed one.
  Packing an existing round needs the user's OK.
- **Prune frozen checkouts (#245).** `python -m task_synthesis.common prune-checkouts` lists the
  `worktrees/tasksynth-run-*` checkouts nothing uses (at least 2 days old; named by no queued or running condor job,
  local process or run metadata modified in the last 4 days; clean except `__pycache__`; HEAD on origin);
  `--remove` removes them with `git worktree remove`.
- **Server swaps (#124).** Each own server has a spare serving name (`<server>b`, run.json `server_spares`) and the
  round's pool lists both. When a server is `[generator] hours - swap_lead_hours` old, the driver submits the spare,
  releases the old server once the spare is healthy, and alternates back 24 h later; sessions move over at the pool's
  5-min refresh (a request cut by the release is retried on a live member). Runs planned before this have no spares.
- **One-shot admission (2026-11-04).** With a one-shot preset (`oneshot`, `off`) the round admits specs by the pool's
  load as well: a spec starts while requests running + waiting stay below `[round] oneshot_target_inflight` (2,000)
  per live server. One-shot specs hold no session between requests, so there is no session cap and `--authors` is 0;
  each job's `--concurrency` is only a ceiling (2x its share of `knee_inflight_per_server`), so the other jobs fill in
  for a lost one. To step the load up during the run (#124: the pilot's ~1,000 running per server used <= 16% KV at a
  0.90 prefix hit; one-shot rounds reached 64k tok/s at ~2,300 in flight), write `<round>/admission.json`, e.g.
  `{"target_inflight": 2500}`. Every job re-reads it within 60 s and logs the change; watch the prefix hit rate
  (keep it > 0.85) and generation tok/s. Without a target, one-shot rounds stay ungated as before.
- **Round jobs that die or hang (#171, 2026-11-05).** A claim names its job (`work/<spec>/.claim/owner`: host, pid,
  shard, owner id), and every job writes a heartbeat `<round>/shards/<owner>.json` every 30 s from its event loop, plus
  a journal of the specs it claims (`<owner>.claims`). A job without a heartbeat for `--claim-stale-minutes` (10) is
  lost: the live jobs take over its open claims (mkdir `.claim/take-<n>`, one winner) and re-run those specs from
  scratch (after a STOP: a `tail_cut` record). Records carry `taken_over_from`; a job that wakes from a stall drops the
  claims it lost and writes nothing for them. A job whose loop has not run for `--hang-exit-minutes` (30) dumps its
  thread stacks to stderr and exits (rc 3). Once its own specs are done, a job exits at once unless other jobs' specs
  are still open and it is the lowest drained shard (that one stays, to take over if their job is lost). Jobs exit
  with `os._exit` after the final flush (stuck executor threads held 2 m1-hero nodes ~40 min), and the job's report
  skips the O(n^2) near-duplicate pass above 3,000 valid tasks (shard 0 of m1-hero never finished it); run
  `round report` for it. If every job is gone (`ALERT`), `round submit` again: the new jobs take over the stale claims.
  Claims made before #171 (text owner) are never taken over.
- **Memory caps on checks (#171).** HTCondor jobs get no delegated cgroup here, and run with an unlimited stack, so a
  task whose crash reproducer recursed without end (m1-hero s1180564-05650, expecting SIGSEGV) took a 384 GiB job and
  its 281 open specs. Now: the job's soft stack limit is Docker's 8 MiB (`--sandbox-stack-kb`), the check sandbox runs
  under the PSS guard at the task's `memory_mb` (`--check-memory-mb` overrides; 8192 if missing; the largest process is
  killed and the generator sees an out-of-memory error), and each build step under a 24 GB resident-memory guard
  (`--build-memory-gb`; not retried). `ulimit -v` is not used: it breaks V8 (wasm) and ASan.
- **Status (#237).** `production status <run> --json` reads every component from its own files with one `condor_q`:
  driver (`<run>/heartbeat.json`, every pass), DeepSeek servers (`endpoints.json`; running / waiting from `/metrics`,
  `--no-metrics` to skip), bind job (`<round>/bind/HEARTBEAT`: results, rate per min, open slots), round jobs
  (`<round>/shards/<owner>.json` every 30 s: claimed / admitted / accepted / cut / errors since the job started, and
  now: open claims, sessions, requests in flight, the pool load it last read), stream producer
  (`<stream>/producer/HEARTBEAT`, chunks, tasks), Super controller and engines (`ops/progress.json`, `owned-jobs.json`,
  `slow-ticks.jsonl`: engines live / cap, active / queued attempts, saved tokens and rate, last tick) and decontam
  (the hold file's work dir: phase, snapshot, pass; its newest work file as heartbeat, since `events.log` is quiet
  while a pass judges). A failing `condor_q` makes every job state `unknown` (an alert of its own), never `gone`.
  `alerts` lists stale heartbeats, held or gone jobs that should be live, a controller tick older or longer than 60 s,
  low /data file quota and the driver's ALERT lines of the last hour: a monitor prints only `alerts`. A claim is not
  an admission: a claimed spec may still wait for its binding and for room on the servers.
- **Re-plan (#238).** `production replan <run> --vocab V --seed N [--mix M] [--asset-share S]` replaces the specs
  nobody has started with new draws (m1-hero's v2h -> v2h0 switch, #165, was done by hand). Dry run by default.
  `--apply`: holds the bind job; pre-claims (`.claim/owner` = `replan-<k>-s<seed>`) the unstarted specs the round
  jobs could start now (binding resolved, inside the bind window); writes `specs.jsonl` = started specs (claimed or
  recorded, in order) + new draws (binding selected as in `plan`; old file in `specs.before-replan-<k>.jsonl`);
  updates `run.json` (recipe, `replans`, `overrides_log`); replaces the bind job (`bind --ramp-minutes`, 15 by
  default: 10% of its slots at once, the rest evenly; m1-hero's 600 started at once into the overload); and waits
  until every live round job reports the new file. Round jobs re-read `specs.jsonl` within 60 s when it changes:
  specs that left it are cancelled where they wait, new ones join the queue, and started sessions go on, so old jobs
  are no longer drained and removed by hand. Jobs started before this code cannot reload: the re-plan refuses, or
  with `--restart-old-shards` removes them and submits a new round job that takes their claims over (#171: their
  in-flight specs re-run from scratch). Refused after STOP, once the round finished, and on a used seed.
- **Admission under load (#238).** `tests/test_admission_load.py` runs 12 jobs x 120 waiting specs of the real gate
  against fake `/metrics` servers (latency grows with concurrent reads; one server times out for 2 s) on a 50x
  compressed clock: running stays <= the target + 10%, nothing is admitted while a load is unknown, and the servers
  refill after. The pre-#170 gate fails it (a timed-out read counts as load 0: ~1.4-1.7x the target).
- **Cluster credits (#227, #241, #242, 2026-11-05).** A job pays for what it *requests*: max(CPUs, RAM GB / 16) + 24
  per GPU, per hour, at no less than the node's floor (`MinRunningPrice`: B200 55, H100 35, A100 15/25, CPU-only 5-35),
  CPU-only jobs on GPU nodes included; long jobs drift toward waiting bids (up to 10%/h). m1-hero cost 1.62M credits at
  floor prices (~3.5M with drift), and **76% of it was CPU and RAM**, not GPUs. What changed:

  | Job | Was (m1-hero) | Now | Why |
  | --- | --- | --- | --- |
  | Super workers | ~101 sized by KV room, never shrank | live attempts + slot shortage + 25%; drain after 15 min (#241) | ~40% of slots were used |
  | Super workers' bid | 40 | 25 for as many as fit on CPU-only/A100 nodes now, the rest 40; idle 5 min -> 40 | 64 of 138 ran on H100 nodes (floor 35) |
  | Round shards' bid | 56 | 25 for as many as fit (`[round] cheap_bid`), the rest 56; the driver rebids idle ones after 5 min | 9 of 12 ran on B200 nodes (floor 55) |
  | Round shards | 64 CPU / 384 GiB | 24 CPU (`cpus_workspace` 64 for `wx`) | 1-3 cores used; builds wait on the network |
  | DeepSeek servers | 1.5 TiB / 768 GiB, CPU KV tier 4 x 64 GiB | 320 GiB / 20 CPUs, no CPU KV tier | the tier served 0% of prompt tokens; replay at 2,000 running: same tok/s (#242) |
  | Super engines | 16 CPU / 320 GiB | 16 / 256 GiB | 215 GiB used; 256 = the 16 CPUs' units |
  | bind | 16 CPU | 8 | 0.6 cores used |

  The fit count (`synth.condor.cheap_capacity`) applies the GPU nodes' reserve for GPU jobs (16 CPUs, 64 GB).
  Job `rank` cannot pick cheap nodes here: `NEGOTIATOR_PRE_JOB_RANK` (fewest GPUs, then the fullest node) orders
  machines first. Only the bid excludes expensive nodes, and big shapes (64 CPU / 384 GiB) fit few nodes, so they
  overflowed onto B200s. **Read at the next hero** (per-minute cgroup logs, new in #242):
  1. DeepSeek `serving/<server>/resources.<job>.jsonl`: `memory_bytes` minus `cache_bytes` (Engram shared memory +
     processes, ~219 GiB in the replay) must stay well under the 320 GiB request; `prompt-sources.<job>.jsonl` confirms
     no CPU-tier traffic is expected (`external_kv_transfer` absent).
  2. Round `rounds/<round>/resources/<owner>.jsonl`: `cores` near 24 for long stretches -> back to 32; memory peaks
     under ~200 GiB with #171's caps -> 16 CPU / 256 GiB.
  3. Super engines `ops/serving/job-N/resources-g<gen>.jsonl` and workers `ops/workers/*/resources.jsonl`.
  4. Controller log: `Draining workers` / `Retired worker` / `rebid to`; slots used vs workers (no long stretch of
     `worker_slot_short` > 0 with engines underfed). Live lever: `{"worker_headroom": 0.5}` in
     `ops/admission-policy.json` (default 0.25) raises the fleet within a tick.
  Needs a B200 replay before changing (#242): the Super CPU tier size (200 GB holds ~46.6M tokens vs a 12-16M working
  set per engine, but 280 vs 200 is the only size tested), and the worker shape (CPUs and slots per worker: workers hit
  their 12-core cap in 25% of samples, so fewer cores per agent may slow tool calls).

### Checks (none tests correctness)

- The package parses: all blocks, clean absolute paths, ≤ 80 files and 1.5 MB of text, a 50–600-word instruction.
- The image builds from the thin layer.
- In an offline sandbox: services start and the services script returns; every declared input exists; no declared
  output exists yet; `defect_check` exits 0 when a defect is declared; `/tasksynth` (construction files) is gone;
  every path the instruction names exists, is under a declared input or output, or has an existing parent.
- The snapshot (tree, heads of the inputs, defect result) goes to the judge, so it scores the built environment
  rather than the author's claims.

The check runs the task's entrypoint, as a campaign does. Docker and harbor_ns give each container a
fresh `/etc/hosts`, so a setup that writes it (`127.0.0.1 lab.local`, a stale `build.internal` the agent must fix)
has its copy saved in the image as `/etc/tasksynth/hosts`, and the entrypoint puts it back at start. Tasks made before
that (15 in rounds r4–raf1, 2 in cohort sonnet55-r6c) are migrated with `$PY -m task_synthesis.pipeline.round rehost
[--round r6c ...]` (rounds and cohorts; a task still being written is skipped).

### Judge

Scores 1–5: clarity, consistency, solvability, difficulty (fit to the target minutes), realism, originality; flags
leaks_solution, needs_internet, needs_gpu, unsafe, spec_mismatch. Pass = clarity, consistency, solvability ≥ 4,
the other scores ≥ 3, and no blocking flag (computed from the scores, not the judge's verdict). v0 uses the generator
as its own judge, so each round also calibrates it against a reading of the tasks.

## Audit protocol

A round is 100 specs with fixed prompts. Between rounds:

1. Read REPORT.md: funnel, failure reasons, judge scores, slices, decon and near-duplicates.
2. Read the failures and 20 random judge-passed tasks (instruction, files, built tree), and note where the judge and
   the reading disagree.
3. Change prompts, checks or spec scope; log the change and its reason in AUDIT_LOG.md; run the next round.

**Quality bar to leave auditing** (two consecutive rounds with unchanged prompts):

| Metric | Bar |
| --- | --- |
| Environment-valid share of specs (≤ 2 repairs) | ≥ 85% |
| Judge pass share of valid tasks | ≥ 75% |
| Random judge-passed tasks read and acceptable | ≥ 18 of 20 |
| Near-duplicate pairs (TF-IDF cosine ≥ 0.6) | ≤ 2% of tasks |
| Decon-flagged tasks | dropped; ≤ 2% of tasks |

Meeting the bar unlocks the next stage (a small Super trajectory pilot), which the user approves.

### Default from 2026-11-02: no idle servers, no tails (user)

The lean2 sandbox run (third real-asset A/B, #20) kept its 3 DeepSeek servers at only ~46% of full load for three
reasons. Static per-round spec lists drained the servers at different times. A fixed author count let the batch shrink
whenever authors sat in commands or builds. And the last ~5% of sessions ran on near-idle servers. Generation runs now
work as follows:

1. **One round, one queue, one server pool.** Put all of a run's specs in one round and submit it with `--jobs N`.
   Every job claims specs from the shared queue; a claim is a mkdir, which is atomic on Lustre. Pass the servers as a
   pool, `--gen gen-a+gen-b+gen-c`. An author session is pinned to one server AND one of its vLLM DP ranks
   (`X-data-parallel-rank`, from the server's launch.json) for all its steps, so its conversation stays
   prefix-cached; new sessions go to the (server, rank) with the fewest live sessions. Each DP rank has its own
   prefix cache, and vLLM's DP balancer ignores prefixes: with server-level affinity only, the 5th A/B pool ran at
   prefix hit ~0.5 with ~4% KV in use. Pools re-read their members every
   5 min and on connection errors, so a server can join a running pool or be released mid-run.
2. **Load-aware admission (agentic/workspace authors; one-shot specs too when a target is set, see "M1 production").** A new author session starts only while two limits hold.
   The pool must have fewer than `--target-inflight` requests (default 1,200) running plus waiting per server, and
   fewer than `--target-sessions` open sessions (default 1,000) per server. Sessions admitted in the last 2 min
   count against both limits. Idle sessions' contexts compete for the prefix cache: ~1,000 sessions per server
   held a 0.76-0.79 prefix hit rate, while ~2,000 dropped it to 0.45-0.5 at KV 31%. `--authors` only caps each
   job's sandboxes; size `--jobs` x `--authors` to about `--target-sessions` x servers. A third limit is the job's
   own CPU: a job admits no new session while more sessions wait for a check_task build slot than it has slots
   (`--build-parallel`, 2 CPUs each). Plan ~3 sessions per CPU (~190 per 64-CPU job, i.e. `--jobs 16` for a 3-server
   pool): with DP-rank pinning an author reaches its builds ~2x sooner, and 375 sessions per 64-CPU job queued
   ~120 builds behind 32 slots while the servers fell to ~15% of their sessions in flight. `round.log` says
   "admission held" when a job is CPU-bound.
3. **Stop at the target, not at the last spec.** Give the round ~1.4x the specs the target needs (pass rates are
   70-85%) and set `--target-tasks`. Once that many tasks are valid and judge-passed, every job cuts its open sessions
   (recorded as `tail_cut`). Specs that never started are recorded as `not_run`, so the stream can end. The small bias
   toward faster specs is accepted. If the specs run out first, the tail rule (`--tail-frac` 3% open for
   `--tail-minutes` 15) cuts the remainder instead.
4. **Release servers at stage ends.** Do not leave a server running for more than about 24 h, or idle. Run the trace
   judge on one server and release the others when authoring stops. Before freeing GPUs that a training job needs,
   queue the training job first.

### Default from 2026-10-31: generation and traces run together (user)

Production runs no longer go round → bundle → campaign in stages. Generation keeps the generator server full and
the trace campaign starts on the first chunk of tasks:

1. **Rounds at full concurrency.** `round submit` puts every spec of a round in flight at once (`--concurrency 0`,
   the default; at most `MAX_IN_FLIGHT` = 2,500 per round) with 48 builds per job (32 CPUs). Split the specs into
   rounds that together stay near the server's knee, ~2,500-3,000 requests per 4xB200 DeepSeek-V4.1-Flash-1017
   server (e.g. four rounds of ~565). 2026-10-31: 300 in flight gave 20.7k gen tok/s at 2% KV; 2,273 in flight gave
   64k gen tok/s at 34% KV, no preemptions, judge pass and network errors unchanged with 192 builds on the proxy.
2. **Stream, not bundle.** Publish judge-passed tasks while the rounds run; the first publish (chunk 0) can take
   every round already finished:
   ```bash
   $PY -m task_synthesis.pipeline.campaign stream --rounds raf3 raf4 --stream /data/aai/tbench/tasksynth/streams/<name> \
       --exclude <bundles already traced> --follow --interval 300 --min-tasks 50 [--end]
   ```
   Add `--end` only once every round the stream will take is listed (a round added later needs a producer restart;
   the producer is restartable, its state lives in the stream).
3. **Campaign with `[train.stream]`** (template: `synth/campaigns/nemotron35-super-tasksynth-swap.toml`), submitted
   as soon as chunk 0 is committed; its smoke tasks are the stream's `smoke.json`. Admission is per serving engine
   (kv_fit on each engine's own KV), so a backlog of streamed tasks never overfills the engines that are up while
   others still queue for GPUs. Real-asset traces carry ~39k tokens of working set per agent: set
   `[admission] agent_tokens_prior = 40000` (the swap campaign started at 30000, overfilled its first engine's KV
   during the ramp, 48 preemptions in 25 min, until kv_fit learned the size).
4. **Token budgets and streams.** A `saved` budget stops in arrival order, so the tasks it leaves untraced are the
   last generated (those that needed repairs). When the traced subset must be unbiased (an A/B), trace every task and
   take a seeded random subset afterwards.
5. **No trace judge in production (from 2026-11-03, #57).** Campaigns run without `traces run`, and SFT data keeps
   every task's traces: no `--drop-tasks` list from judge verdicts. Student 1 without its trace-judge filter (326
   flagged tasks back in, 6% of train tokens) was not worse on tbmix: 44.4% vs 39.2%, paired +5.2 pp [-0.0, +10.6],
   equal val BPB; the gap is read as checkpoint noise (#105), not a gain. The judge cost ~50 B200-h per 1B training
   tokens and removed ~5% of tasks. `traces run` stays as an audit tool (e.g. after a generator or prompt change): start it with the campaign
   (it streams and exits once the campaign is complete; `--once`: one pass; `--per-task 1`: one trace per task;
   `--judge gen-a+gen-b` pools servers). Periodic passes fell behind: each waits on its slowest verdict (1-2 h).

- Tasks declare `network_mode = "no-network"`: the agent has no route out; Pi reaches the model through
  `synth.environment`'s loopback relay. Image builds use the job's package cache (then the proxy).
- `tests/test.sh` writes reward 0 and `final_state.json` (each declared output's size, sha256 and head, plus a file
  tree), since the tasks ship no verifier.
- `pipeline/traces.py`: per-trace tokens, turns, minutes, tools, install attempts that failed offline, and a DeepSeek
  judge of each trace (instruction + private sketch + condensed trace + final state → solved/partial/failed, cause,
  task defect, too easy). State and REPORT.md in `/data/aai/tbench/tasksynth/traces/<campaign id>/`.

## v0 scope and known gaps

- Buckets `none` and `best-generated` only; specs needing a sourced asset, an upstream project or a VM image are
  redrawn. Asset sourcing comes later.
- Builds reach apt/PyPI through a package cache in each round job (synth/README.md "Package cache", #60): repeats
  come from node-local disk, the cluster proxy sees misses and index revalidations only. Agents' apt in offline
  sandboxes goes through the campaign worker's cache; their pip still tunnels to PyPI (opt-in:
  `harbor.package_cache_pip`). Authors' sandboxes send their apt and pip through the round job's cache too
  (`--author-package-cache`, default `apt+pip`; their other HTTPS keeps the cluster proxy).
- No per-sandbox disk limit yet.
- One judge (the generator). A second judge model is an option if the reading disagrees with it.
- No output cap on generator or judge replies: only the 132k context bounds them (REPORT.md counts truncated replies).
- Client timeout (`pipeline/llm.py`, 6 h per request, queue time included) must exceed the slowest legitimate reply:
  under full load DeepSeek decodes ~17 tok/s per request and replies run to ~100k tokens. The old 1 h cut 14% of the
  #25 D2/D3 generator replies (each restarted from scratch: ~23% of generator decode wasted) and stalled trace-judge
  passes for hours on their longest verdicts. Check after launch: records' `gen_seconds` far above completion / rate
  means retries. Don't bound replies with `max_tokens` near the context: prompt + cap > 132k is rejected (400).
- A slow campaign is usually supply-limited: if `ops/progress.json` shows few `missing_trajectories` and a low
  `active_train`, Super is starved and the rounds (DeepSeek) are the bottleneck; saturate the DeepSeek servers first.

## Real assets (issue #20, from 2026-10-31)

A spec can be bound to a real, public asset before generation. The spec keeps everything it had (class, formats,
domain, action, target minutes, authored companions); only the anchor becomes real.

```
spec ─► target (class × formats × domain; the agent action is left out, so one asset can serve several tasks)
     ─► query planner (DeepSeek, per cell and catalog) ─► catalog search (metadata only) ─► license filter
     ─► shortlist (DeepSeek, spec + up to 16 candidates) ─► fetch (pinned, size-capped) ─► scrub ─► asset store
     ─► fit check (DeepSeek, spec + manifest): fit? which files to ship?   (up to 3 candidates per spec)
     ─► export: the round's specs carry the binding; per spec asset.tar.zst + the generator's and judge's views
     ─► round as before: generator sees the asset's files (code in full, data by manifest); setup reads
        /tasksynth/asset/; judge adds asset_use (core criterion, >= 4 to pass)
```

| Piece | Code |
| --- | --- |
| Catalog adapters (GitHub repos/files, Zenodo, HF datasets/models, OpenML, Commons, arXiv, Europe PMC, Wikipedia, Gutenberg, RCSB, NCBI, PubChem, MassBank, COD, Ubuntu packages) | `assets/sources/` |
| Routing of a target to catalogs | `assets/targets.py` |
| Store: one tar.zst per asset, JSONL records (URL, version, SHA-256, license, attribution, manifest) | `assets/store.py` |
| Licensing policy (redistributable / pointer / excluded) | `assets/license.py` |
| Secrets and e-mail scrubbing (git: e-mails rewritten, secrets in history reject) | `assets/scrub.py` |
| Manifest (tree, types, heads, per-format stats) and the generator's/judge's views | `assets/manifest.py`, `assets/render.py` |
| Binding: plan, search, shortlist, fetch, fit; report; export to a round | `assets/bind.py` |

```bash
APY=/data/aai/venvs/tasksynth-assets/bin/python   # pandas/pyarrow/Pillow/openpyxl for manifests
$APY -m task_synthesis.assets.bind submit --name <bind> --specs <specs.jsonl>          # CPU job, needs gen-ds
$APY -m task_synthesis.assets.bind export --name <bind> --round <round> --prefix <p>   # bound specs -> round
$PY  -m task_synthesis.pipeline.round submit --round <round> --n <bound count>         # as before
```

State: `/data/aai/tbench/tasksynth/assets/{store,index,binds,specs}/`. A spec whose candidates all fail the fit
check stays unbound; in the A/B against student 1 it keeps its generated task.

## Spec vocabulary v2 (issue #25, from 2026-10-31)

`--vocab v2` on a round (or `sample_assets.py --vocab asset_sampler/vocab_v2.json`) draws specs from a vocabulary
that Opus 5.5 brainstormed (`vocab/brainstorm.py`, 185 cached `claude -p` calls in
`/data/aai/tbench/tasksynth/vocab/v2/`; `vocab/build.py` writes `vocab_v2.json`).
Since 2026-11-04 rounds draw from `v2h0` by default (`specs.DEFAULT_VOCAB`; `v2h` from 11-03): v2 without the new
top-level options. `--vocab v1` draws the TB-fitted v1 exactly as before.

- **Top level:** 4 new actions, 5 new domains, 5 new asset classes. Each passed an Opus review: as broad as a typical TB
  option, no overlap, feasible in the sandbox, not niche; four class candidates became formats of existing classes.
  New options get 25% of each dimension (`cap_new`). TB options keep their fitted, tempered shape in the other 75%.
  Opus compatibility labels decide *where* a new action or domain appears; their marginals are equalized, so each new
  option is about as common as a typical TB option. New classes pair by Opus labels, normalized to keep the cap.
- **Sub-domains:** 76–116 per domain, 1,737 in all: iterative "not yet covered" passes, a cleaning call, then a
  coverage check on 1,300 student-1 tasks. Drawn uniformly within the domain; 20% of specs draw none
  (`open_subdomain`). The generator sees `Domain: <domain>; area: <sub-domain>`.
- **Formats:** 271 new formats, services and git states, tagged by domain. They get half of a class's draws
  (`new_format_share`), and only those common in the drawn domain take part. Details that name a defect are merged:
  `wal-journal` into sqlite, `secret-in-history` and `lost-commit` into `rich-history`; `encrypted` and `polyglot` are
  dropped (#19).
- **Languages (other-code):** 84 languages weighted by real-world share ** 0.4, with no TB boost (v2, v2h). `v2h0`
  adds a floor: every language seen in a TB release's other-code assets gets at least 1% of draws (`language_floor`). The TB languages
  without an offline toolchain (e.g. Lean, Julia, VBA) are kept, and the generator is told the code can be read but
  not run.

Pilot: rounds `rv2a` (v2) and `rv1a` (v1 control). Compare them with `python -m task_synthesis.vocab.pilot_metrics`
(numpy). It reports theme concentration, nearest-neighbour similarity, package variety and judge results.

**Variants** (same options, other weights; results in AUDIT_LOG.md and #25):

| `--vocab` | What differs from v2 | Use |
| --- | --- | --- |
| `v1` | the TB-fitted vocabulary before #25 (no new options) | students 1-2, #20, #26; comparisons with them |
| `v2` | (25% new options, 20% open sub-domain draws) | the #25 v2 arm |
| `v2d2`, `v2d3` | flatter / flat weights | #25 dose-response arms only: both lost to v2 |
| `v2h` | open sub-domain draws 5% | default 11-03 to 11-04: open draws cause most same-concept repeats at scale |
| `v2h0` | `v2h` with `cap_new` 0 (no new actions, domains or classes) and TB's 22 other-code languages at >= 1% of draws | **the default**: two seeds per arm put v2 level with student 1 on tbmix and 1.3 pp below on full TB2.1, from diluting TB2.1's (mostly code-anchored) task types |

To reproduce or compare with an earlier round, name its vocabulary and add `--minutes-mix student1` (#25's arms and
students 1-2 predate #26's easy-heavy default): `--vocab v2 --minutes-mix student1` redraws `rv2a`'s specs
byte-identically, and `--vocab v1 --minutes-mix student1` redraws student 1's `r6a`.
